User Guide

This guide covers every construct the converter handles, the options that influence it, and the fallback used when HTML has no Markdown equivalent.

#Installation

Add the crate to your manifest and enable only the features you need.

This section describes how the converter treats installation. The behavior follows the CommonMark specification wherever a direct equivalent exists, and documents each fallback where it does not.

In practice, most documents need no configuration at all. When they do, the Options struct exposes a small set of switches, each of which is described below together with an example of its effect on installation.

A common source of confusion is the difference between rendered equivalence and textual equivalence. Two Markdown strings may differ byte for byte yet render to the same HTML; the converter aims for the former, and the test suite checks it for installation.

Example

use htmd::HtmlToMarkdown;

fn main() {
    let converter = HtmlToMarkdown::builder()
        .skip_tags(vec!["script", "style"])
        .build();
    let md = converter.convert("<h1>Installation</h1>").unwrap();
    assert_eq!(md, "# Installation");
}

Rules

  • Rule 1.1: when the input contains <p>, the installation handler preserves it.
  • Rule 1.2: when the input contains <em>, the installation handler normalizes it
    • see also Configuration options
    .
  • Rule 1.3: when the input contains <a>, the installation handler escapes it.
  • Rule 1.4: when the input contains <li>, the installation handler re-indents it
    • see also Lists and list items
    .
  • Rule 1.5: when the input contains <td>, the installation handler wraps it.

#Installation (part 2)

Add the crate to your manifest and enable only the features you need.

Note that browsers are lenient about malformed markup, and the parser mirrors that leniency: unclosed <p> elements, stray end tags, and misnested formatting are repaired exactly as the HTML5 tree-construction algorithm prescribes.

This section describes how the converter treats installation (part 2). The behavior follows the CommonMark specification wherever a direct equivalent exists, and documents each fallback where it does not.

In practice, most documents need no configuration at all. When they do, the Options struct exposes a small set of switches, each of which is described below together with an example of its effect on installation (part 2).

Example

$ cargo add htmd
$ cargo test --test installation-2_tests
   Compiling htmd v0.5.0
